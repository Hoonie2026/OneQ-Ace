# 002. 학습 DB·백업 형식과 기록 재연결 규칙 (3단계)

- 상태: 확정 (2026-10-14, 세션 #3)
- 관련: 개발기준서 4.2, 4.3, 7.1, 8장 3단계

## 결정

1. **본 DB 이름은 `oneq`**(Dexie v1). 0단계 검증 DB `oneq-stage0`과 섞지 않는다. 설정 화면에서 0단계 데이터(약 30MB)를 따로 지울 수 있다.
2. **4.2 표 대비 추가·변경**
   - `attempts`: `uid`(고유, 백업 합치기 키), `contentHash`(재연결 키), `unsure`(헷갈림 체크 — 4단계에서 정답이어도 FSRS Hard) 추가. 기본키는 자동증가 그대로.
   - `notes`: `contentHash` 추가.
   - `runs`(신규): 풀이 묶음(회차 전체·과목별·오답 다시 풀기)과 이어 풀기 위치. `sessionId` = attempts.sessionId.
   - `cards`: 스키마만 두고 4단계에서 채운다. 원장(attempts)에서 다시 계산할 수 있으므로 팩 삭제 시 보관하지 않는다.
3. **불변식: attempts·notes의 qid는 항상 존재하는 문항을 가리킨다.** 잇지 못한 기록은 `orphans`(매핑 대기)로 옮기고, 팩을 가져올 때마다 자동으로 다시 잇는다. 팩을 삭제해도 기록은 지우지 않고 매핑 대기로 보낸다.
4. **재연결 순서(4.3 보완)**: ① qid와 contentHash가 모두 같으면 유지 ② **같은 팩 안에서** contentHash가 같은 문항으로 이동(재전처리로 번호가 바뀐 경우) ③ qid만 있으면 내용이 고쳐진 것으로 보고 유지(contentHash 갱신) ④ 나머지는 매핑 대기.
   - contentHash 검색을 같은 팩(packId)으로 한정한다. 측량 기출은 회차 간 같은 문제가 그대로 반복되므로, 팩 전체에서 찾으면 풀지 않은 다른 회차에 기록이 붙어 진도·점수가 잘못 집계된다.
5. **팩 교체**: 같은 packId는 packVersion이 높을 때만 교체, 같은 버전은 확인 후 다시 저장, 낮은 버전은 거부.
6. **백업 형식 `oneq-backup` v1**(.json): settings + attempts + notes + cards + runs + orphans + 팩 목록(packId·버전·이름) + **기록 지문**. 문항·이미지는 넣지 않는다(팩을 다시 가져오면 기록이 이어짐). formatVersion 0(0단계 시험용)은 거부.
7. **복원은 합치기**: 같은 uid의 풀이는 건너뛰고, 메모는 수정일이 최신인 쪽, runs는 updatedAt이 최신인 쪽. 팩보다 백업을 먼저 복원해도 기록은 매핑 대기로 보존된다.
8. **기록 지문**: attempts(+매핑 대기 풀이)와 notes(+매핑 대기 메모)를 정렬해 SHA-256 앞 8자리. 게이트의 "기록 100% 일치"를 사람이 화면 숫자로 비교하는 수단. 빈 기기에 복원하면 백업 때 지문과 같아야 한다.
9. **백업 권유 배너**: 새 기록이 있고 마지막 백업(없으면 첫 풀이) 후 7일, 또는 백업 후 300건.
10. **내보내기**: 다운로드(.json) 기본, 공유 시트(.txt, `files`만 전달) 보조 — 0단계 실측 그대로.

## 검토했으나 보류

- 매핑 실패 기록을 attempts에 남긴 채 표시만 숨기기: 집계 코드마다 예외 처리가 필요해 불변식(3)을 택함
- 복원 = 덮어쓰기: 다른 기기의 기록을 실수로 지울 수 있어 합치기를 택함
- 기록 지문 대신 건수만 비교: 같은 건수에 내용이 다른 경우를 못 잡음
