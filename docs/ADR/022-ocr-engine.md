# ADR 022 — 스캔본 OCR 엔진: Windows 내장 OCR(PREP-PLAN-v0.5 B1)

- 상태: 결정(사용자 2026-11-11 16:59 "동료 PC에도 내장되어 있는 것만으로")
- 근거 자료: 🖥P5 비교(`oneq_prep/ocrbench.py`, 정답 `tests/fixtures/ocr/railway-2010-2-gt.json`), 표본 `source_pdf/철도보선기사_스캔본.pdf`(2010년 2회, 10쪽, 실제 종이 스캔 ≈120dpi)

## 비교 결과(사용자 PC, Windows 11, CPU, 파이썬 3.11)

| 엔진 | 본문 글자 맞춤(×2) | 95%↑ 단위 | 정답표 100개(칸 나눠 읽기) | 쪽당 |
|---|---|---|---|---|
| **Windows 내장(winocr, ko)** | **92.9%** | 59.2% | **100/100** | **1.1초** |
| Tesseract 5(kor) | 89.8% | 44.9% | 100/100 | 3.1초 |
| PaddleOCR 3.7(PP-OCRv5 한국어) | 23.8% | 0% | 0/100 | 약 130초 |

- PaddleOCR: PaddlePaddle 3.3은 oneDNN과 충돌(`ConvertPirAttribute2RuntimeAttribute`), 3.2.2 + `enable_mkldnn=False`에서도 무거운 글자 찾기 모델(server_det)은 추론 중 C++ access violation, 가벼운 모델은 돌지만 한글을 한자·가나로 읽고 쪽당 2분 이상. 크기(+600MB)·실행파일 묶기·동료 PC 충돌 위험까지 → **제외**. 외부 분석(제미나이)의 `enable_mkldnn=False` 처방은 이미 적용된 상태였고 제시 코드는 PaddleOCR 2.x 문법이라 3.7에 맞지 않음
- 정답표는 쪽 통째로 읽으면 세 엔진 모두 낱자를 건너뜀(5~9/100) → **표 격자를 칸으로 자르고, 답 줄마다 칸을 이어 붙인 한 줄 그림으로 읽기**(Tesseract는 psm 7, 가나다라 밖 비슷한 글자 보정, 번호 줄은 건너뜀) → 두 엔진 모두 100/100

## 결정
1. 스캔본 OCR = **Windows 내장 OCR만**(배포 설치 프로그램에 다른 엔진 넣지 않음). 한국어 Windows는 한국어 OCR 기능이 보통 미리 설치됨(사용자 PC 🖥P3 확인). 없으면 Windows 11은 일반 사용자도 [설정 → 시간 및 언어 → 언어 및 지역 → 한국어 → 언어 옵션]에서 추가 가능(회사 정책으로 막혔으면 IT) — 전처리기가 스캔본을 만났는데 기능이 없으면 이 경로를 안내
2. OCR은 스캔본에만 필요 — 글자 PDF(comcbt 교사용 등)는 OCR 없이 처리
3. 기존 Tesseract 경로(`ocr.py`)는 지우지 않고, 직접 설치된 PC에서만 예비로 자동 사용
4. 끝 쪽 정답표는 칸 나눠 읽기(ocrbench의 `table_rows`·`_strip`·`_letters`를 본 경로로 옮김). **손글씨 ✓ 표시는 정답으로 쓰지 않음**(표본 1번·9번 모두 시험 본 사람의 오답 표시)
5. 보기 번호 **가나다라**도 읽음(지금 파서는 ①~④ 전제)
6. 글자 맞춤 92.9%는 완벽하지 않음("시엔트" 등) → 스캔본 문항은 지금 설계대로 `ocr`·`needs-review` 표시, 의심 문항만 검수
7. 🖥P14 때 동료 PC 한 대에서 한국어 OCR 기능 기본 설치 여부 확인(`Get-WindowsCapability -Online | ? Name -like 'Language.OCR*'`)

## 구현(세션 #16, 2026-11-11 — PREP-PLAN B1 ①~④)
- `oneq_prep/ocr.py`: 엔진 고르기 `pick_engine()` = Windows 내장(winocr, ko) → 없으면 직접 설치된 Tesseract → 둘 다 없으면 `OcrUnavailable`(Windows면 [설정 → 시간 및 언어 → 언어 및 지역 → 한국어 → 언어 옵션] 안내 + IT 요청 문구). `ONEQ_OCR_ENGINE`으로 강제(실측용). winocr 결과(lines → words → bounding_rect)를 공통 단어 상자로 → 글자 좌표. 렌더 배율은 긴 변 3000px 상한(표본 ≈ ×2.1 — 120dpi 스캔을 300dpi로 늘려도 느리기만 함)
- 낱말 사이 공백: 글자 높이 0.6배보다 넓을 때만(표본 실측: 낱자 사이 0.2~0.5, 단어 사이 0.7~1.0) — 엔진마다 단어를 나누는 방식이 달라도 같은 글
- **가나다라 보기**(5절): "가." 꼴 토큰(줄 첫머리·넓은 간격 뒤, "가"+"." 따로·"가.일정" 붙음 포함)을 번호 1~4로. 문항 안에서 마지막 "라"부터 거꾸로 다·나·가를 골라 줄바꿈된 "다." 같은 잡음을 거름. 셋만 읽히면 2×2 배치로 빈 자리 채움. 칠한 표시 판정(`mask_ocr_filled`)은 가나다라 보기에 쓰지 않음 → **손글씨 ✓는 정답이 되지 않음**(4절)
- **정답표**(4절): 끝 쪽부터 격자 표를 찾아 `read_answer_rows`(ocrbench에서 옮김)로 읽고 그 쪽은 문항 찾기에서 뺌. 번호 줄을 OCR이 "다 라"로 잘못 읽어 칸이 10개 밀리던 문제 → 숫자가 칸 수의 1/3 이상이면 번호 줄, 답 줄은 가나다라가 칸 수의 70% 이상. 정답은 **시험지 번호**로 붙임
- 스캔본 배치(표본에서 드러난 것): 단 구분 = 가운데 35~65% 중 글자가 가장 덜 덮는 x(표본은 52%), 단 왼쪽 끝 = 쪽·단마다 문항번호 줄 x를 높이에 대한 직선으로(종이 기울기 — 2쪽은 위 59pt → 아래 42pt), 크롭 폭은 글줄 실제 범위, 꼬리말("A-9-1-1760")은 쪽 아래 8% 안 한글 없는 줄로 빼기
- 문항번호를 못 읽은 문항: 읽은 번호가 1~3 건너뛰면 그 번호를 믿고, 빠진 번호는 앞 문항의 "라" 줄 뒤에서 문항번호 자리에서 시작하는 줄을 찾아 되찾음(경고 "위치로 찾음"). 순서로 매긴 번호 뒤에 진짜 번호가 나오면 앞 문항의 이어지는 줄로 합침. 끝내 못 찾은 번호는 `manifest.excluded`(unreadable)로 빼고 검수에서 "검수 마침"을 누르면 팩을 만듦. 과목명을 못 읽은 머리말("제 3 과목 : ;")은 출제기준 순서의 과목으로
- 시행일·회차: 스캔본은 첫 쪽 위쪽만 OCR해 처리 전 목록에도 회차를 보여 줌(파일별 기억). "2010년 기사 제2회"(옛 시험지 머리) 읽기 추가 → `RAILTRACK-2010-2`, 시행일 모름
- 창 프로그램: 스캔본이 목록에 있는데 OCR을 못 쓰면 처리 전에 노란 안내 상자(1절 경로). 실행파일 `OneQ-Prep.exe --ocr-check [ko|en]`(종료 코드 0 읽힘·1 Tesseract만·3 기능 없음·4 실행파일에 winrt 빠짐), 명령줄 `py -3 -m oneq_prep.ocr --check`. GitHub 빌드가 실행파일로 영어 OCR을 불러 winrt 묶기를 확인
- 배포: `requirements.txt`에 `winocr; sys_platform == "win32"`(winrt-* MIT), PyInstaller에 winrt 하위 모듈 모두. THIRD-PARTY-NOTICES 갱신
